# Project Pilot

토이 프로젝트에서 스펙을 기준으로 기능을 설계하고, 기능별 FE/BE 작업을 나누어 사용자 확인을 거쳐 개발하는 AI 스킬입니다. 스킬 이름은 `project-pilot`입니다.

프로젝트 맥락을 대화 이력에만 의존하지 않고 `doc/spec/`에 보존합니다. 기능 설계와 조회에서는 스펙을 우선 사용하고, task 상세 설계와 개발에서는 필요한 코드만 확인합니다.

## 설치와 관리

Node.js와 `npx`, 원본 GitHub 저장소에 대한 접근이 필요합니다. **실제로 개발할 프로젝트 루트에서** 설치합니다.

```bash
npx skills add Kchangwook/AI-Native --skill project-pilot --agent codex -y
```

해당 프로젝트에 스킬을 설치하는 명령입니다. 별도 npm 패키지나 서비스 등록 없이 GitHub에 공개된 스킬 폴더를 내려받습니다. 비공개 저장소라면 저장소 접근 인증이 필요합니다.

최신 버전으로 업데이트:

```bash
npx skills update project-pilot -p -y
```

제거:

```bash
npx skills remove project-pilot --agent codex -y
```

설치된 스킬 확인:

```bash
npx skills list
```

원본 저장소에 push된 버전이 설치·업데이트 대상입니다. 로컬에서만 수정한 내용은 배포되지 않습니다. 명령 옵션은 [Skills CLI 문서](https://github.com/vercel-labs/skills)를 참고하세요.

## 사용 방법

Codex에서 스킬을 명시해 요청합니다.

```text
$project-pilot TodoList 만들어줘.
```

| 요청 예시 | 수행 범위 |
|---|---|
| TodoList 만들어줘 | 기능 설계부터 시작하고 각 단계에서 확인 대기 |
| 로그인 기능 추가해줘 | 기존 확정 스펙을 기준으로 변경 설계부터 시작 |
| 로그인 기능 설계해줘 | 기능 설계까지만 수행 |
| 승인된 설계를 작업으로 나눠줘 | 작업 분해와 계획 확인까지만 수행 |
| 이 설계대로 구현해줘 | 설계·계획의 승인 상태를 확인하고 빠진 단계부터 수행 |
| 현재 로그인 스펙 알려줘 | 확정 스펙 조회·설명만 수행 |
| 추가할 만한 기능은? | 관련 스펙 조회 후 아이디어 제안만 수행 |
| 잠시 멈춰 / 계속해줘 | 현재 상태 저장 후 중단 / 저장 지점에서 재개 |

## 실행 흐름과 사용자 확인

```text
빈 프로젝트라면: 기술 스택·기본 구조 결정 → 사용자 확인
                                          ↓
                                      기능 설계
                                          ↓
                                      사용자 확인
                                          ↓
                                      작업 분해
                                          ↓
                                      사용자 확인
                                          ↓
                         새 채팅: task 1 상세 설계
                                          ↓
                                      사용자 확인
                                          ↓
                              개발·검증·리뷰
                                          ↓
                                      결과 확인
                                          ↓
                         새 채팅: task 2 상세 설계
                                          ↓
                                    같은 순서 반복
                                          ↓
                                전체 검증·최종 확인
                                          ↓
                              확정 스펙·색인 함께 반영
```

각 확인 지점에서는 결과를 설명하고 명시적인 응답을 기다립니다. 최초의 “만들어줘”나 앞 단계의 승인이 이후 단계의 승인을 대신하지 않습니다. 문맥이 명확한 “ㅇㅇ”, “ㅇㅋ”, “진행해”는 현재 확인 대상에 대한 승인으로 처리할 수 있습니다. 질문이나 스펙 조회는 승인으로 취급하지 않습니다.

수정 요청을 받으면 현재 단계를 보완하고 다시 확인받습니다. 변경이 상위 기능 설계나 계획에 영향을 주면 해당 부분부터 재확인합니다.

## 단계별 동작

### 1. 빈 프로젝트 기본 설정

저장소 또는 일반 폴더가 비어 있으면 기능 설계 전에 실행 형태, 기술 스택, 저장 방식, 주요 디렉토리와 실행·검증 방식을 제안합니다. 이미 지정한 선택은 유지하고 부족한 내용만 질문합니다.

빈 상태는 사용자 설명이나 루트 항목 이름을 최소한으로 확인해 판단합니다. 스펙이 없다는 이유만으로 빈 프로젝트라고 단정하지 않습니다. 기본 설정을 승인받아도 바로 초기화하거나 패키지를 설치하지 않고, 해당 작업을 개발 계획에 포함합니다.

### 2. 기능 설계

확정 스펙을 읽고 목적, 기능 범위, 사용자 흐름, 동작 규칙, 완료 기준을 정리합니다. 필요한 FE/BE 계약과 데이터 구조도 포함합니다. 이 단계는 코드 탐색 없이 진행하며, 부족한 정보는 질문합니다.

### 3. 작업 분해

승인된 설계를 먼저 기능별로 나누고, 각 기능 안에서 FE/BE task를 분리합니다. 한 계층만 필요한 기능은 해당 task만 만듭니다. 기반 작업이 필요하면 선행 작업으로 배치하고 의존 관계에 따라 순서를 정합니다.

```text
할 일 추가
├── BE: 저장 로직·추가 API
└── FE: 입력 UI·API 연결

할 일 조회
├── BE: 조회 API
└── FE: 목록 UI·API 연결
```

각 task에는 구현 범위, 의존 관계, 완료 조건, 검증 방법을 기록합니다. 작업 계획 전체를 확인받은 뒤 task 수행을 시작합니다.

### 4. task 상세 설계

task를 수행할 차례에 별도 채팅에서 구체적인 구현 방법을 설계합니다. 변경·생성할 파일과 책임, 처리·데이터 흐름, FE 또는 BE 구현 방식, 연결 지점, 검증 방법을 정리합니다.

개발 준비 단계이므로 해당 task에 필요한 코드·설정만 읽을 수 있습니다. 상세 설계 확인 전에는 코드 수정·프로젝트 초기화·패키지 설치를 하지 않습니다. 작업 분해 승인과 상세 설계 승인은 별개입니다.

### 5. 개발·검증·리뷰

승인된 task 하나만 구현하고 완료 조건에 따라 검증합니다. 리뷰는 스펙·상세 설계 일치, 작업 범위, 정상 동작, 기존 기능 영향, FE/BE 계약, 코드 품질을 확인합니다.

발견한 문제를 보완한 뒤 구현 내용, 실제 검증 결과, 남은 문제, 직접 확인할 방법을 제시하고 기다립니다. 결과 승인 후 다음 task로 넘어갑니다. 구현 방식에 중요한 변경이 필요하면 상세 설계부터 다시 확인받습니다.

### 6. 전체 검증과 최종 확정

모든 task의 결과 확인이 끝나면 연결된 사용자 흐름을 검증하고 별도의 최종 확인을 받습니다. 마지막 task의 결과 승인이 전체 최종 승인을 대신하지 않습니다. 최종 확인 후에만 확정 스펙과 조회용 색인을 함께 갱신합니다.

## task마다 새 채팅

계획 채팅에서는 기본 설정·기능 설계·작업 분해를 수행합니다. 각 task는 별도 새 채팅에서 상세 설계부터 결과 확인까지 수행합니다. FE/BE task도 각각 별도 채팅을 사용합니다.

- 같은 프로젝트와 같은 체크아웃을 사용합니다. 별도 요청 없이 worktree·브랜치를 만들지 않습니다.
- 새 채팅은 대화 이력을 복제하지 않고 진행 상태와 연결된 문서를 읽습니다.
- 자동 생성에는 실행 환경의 채팅 생성 도구와 사용자의 생성 요청·승인 근거가 필요합니다. 스킬 설치만으로 모든 환경에서 자동 생성이 보장되지는 않습니다.
- 도구가 없거나 사용할 수 없으면 새 채팅용 인계 프롬프트를 제공하고 대기합니다.
- 인계 후 원래 채팅은 해당 작업을 병행하지 않습니다. 동일 task의 중단·재개는 기존 task 채팅에서 이어갑니다.
- 마지막 task 채팅에서 전체 검증과 최종 확인까지 수행합니다.

자동 생성을 원하는 경우 요청에 다음과 같이 명시할 수 있습니다.

```text
$project-pilot TodoList 만들어줘. 각 task는 새 채팅을 생성해서 진행해줘.
```

## 스펙과 진행 상태

경로는 **대상 프로젝트 루트 기준** `doc/spec/`입니다. 설계·개발 중 필요한 첫 기록 시 생성합니다. 조회만 요청했을 때는 파일이나 디렉토리를 만들지 않습니다.

```text
doc/spec/
├── index.yaml                  # 최종 확정된 프로젝트 구성·조회 색인
├── features/
│   ├── <feature-id>.yaml        # 작은 프로젝트의 확정 기능 스펙
│   └── <domain>/               # 규모에 따라 도메인별로 분리
│       ├── index.yaml           # 해당 도메인의 조회 색인·공통 규칙
│       └── <feature-id>.yaml
├── drafts/
│   └── <change-id>/
│       ├── project.yaml        # 필요 시 기술 스택·기본 구조 초안
│       ├── design.yaml         # 기능 설계
│       ├── plan.yaml           # 기능별 FE/BE 작업 계획
│       └── tasks/
│           └── <task-id>.yaml  # task 상세 설계
└── progress.yaml               # 작업 상태·승인·채팅 인계·재개 지점
```

스펙은 YAML로 구조화합니다. 기능에는 고유 ID를 부여하고, 기능이 늘면 관련 도메인으로 자동 분리해 색인과 참조를 함께 갱신합니다. 색인은 필요한 파일을 찾기 위한 안내이며 상세 동작을 중복 저장하지 않습니다.

| 구분 | 저장·반영 시점 |
|---|---|
| `drafts/` | 설계·계획·개발 진행 중 갱신 |
| `progress.yaml` | 단계 시작·주요 진행·확인 요청과 응답·중단·인계 시 갱신 |
| `features/`, 조회용 `index.yaml` | 전체 개발·검증의 최종 확인 이후 함께 반영 |

기존 기능 변경 중에는 이전 확정 스펙을 유지합니다. 기능 설계 승인과 구현 완료, task 상세 설계 승인과 개발 결과 승인은 각각 구분합니다. 중단 시 완료한 일, 남은 일, 다음 행동과 확인 대상을 보존합니다.

## 독립적인 스펙 조회

일반 조회는 프로젝트 색인 → 필요한 도메인 색인 → 관련 기능 스펙 순으로 읽습니다. 전체 코드를 다시 읽지 않습니다. 문서에 없는 내용은 “스펙에서 확인되지 않음”으로 설명하고 미구현으로 단정하지 않습니다. 추가 코드 확인은 사용자가 요청·허용한 경우에 수행합니다.

진행 중인 변경을 물으면 초안과 진행 상태도 읽어 확정 내용과 구분합니다. 확장 아이디어는 현재 스펙을 근거로 제안하되 스펙 수정이나 개발을 시작하지 않습니다. 제안이 채택되고 설계·구현 요청이 들어오면 파이프라인에 진입합니다.

## 스킬 자체의 수정 범위

스킬 내용은 원본 `Kchangwook/AI-Native` 저장소의 `skills/project-pilot/`에서만 수정합니다. 다른 프로젝트의 설치본·전역 설치본·심볼릭 링크의 원본은 사용 중 자동 수정하지 않습니다. 개선점은 제안하고 원본 저장소에서 변경합니다.

이 규칙은 AI 행동 지침이며 운영체제 파일 권한 잠금은 아닙니다. 대상 프로젝트 코드와 스펙의 승인된 변경, 사용자가 요청한 스킬 설치·제거·배포 버전 업데이트는 가능합니다.
