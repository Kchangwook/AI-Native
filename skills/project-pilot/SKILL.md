# Project Pilot

프로젝트의 `doc/spec/`를 지속적인 맥락으로 사용한다. 경로는 파일시스템 루트가 아닌 대상 프로젝트 루트 기준이다. 사용자에게는 한국어로 설명하되 기존 프로젝트의 명명 관례를 따른다.

## 요청에 따른 진입

| 요청 | 읽을 지침 | 실행 범위 |
|---|---|---|
| 만들어줘, 기능 추가·변경해줘 | [설계](references/design.md) | 설계부터 시작하여 각 확인 지점에서 대기 |
| 설계해줘 | [설계](references/design.md) | 설계까지만 수행 |
| 승인된 설계를 작업으로 나눠줘 | [작업 분해](references/planning.md) | 작업 계획까지만 수행 |
| 이 설계대로 구현해줘 | [진행 상태](references/progress.md) | 설계·작업 계획의 확인 상태를 점검하고 빠진 단계부터 진행 |
| 계속해줘, 잠시 멈춰 | [진행 상태](references/progress.md) | 저장된 현재 지점에서 재개 또는 중단 기록 |
| 스펙 알려줘, 추가할 기능은? | [스펙 조회](references/query.md) | 조회·설명·제안만 수행 |

진입할 때 필요한 문서만 읽는다. 작업 개발 시 [개발](references/development.md), 리뷰 시 [리뷰](references/review.md)를 읽는다. 문서를 쓰거나 재구성할 때 [스펙 저장 구조](references/spec-storage.md)를 읽는다. 여러 요청이 섞이면 사용자가 요청한 범위를 함께 고려한다.

## 공통 실행 규칙

- 기본 파이프라인: 설계 → 사용자 확인 → 작업 분해 → 사용자 확인 → 작업별 개발·검증·리뷰 → 각 작업 사용자 확인 → 전체 검증 → 최종 확인.
- 각 확인 지점에서 결과를 제시하고 명시적인 진행 응답을 기다린다. 앞 단계 승인이나 최초의 “만들어줘”는 이후 단계의 승인을 대체하지 않는다. 다음 단계의 구현을 미리 시작하지 않는다.
- 수정 요청은 현재 단계에서 반영하고 다시 확인받는다. 확정된 설계에 영향을 주면 설계부터, 작업 계획에만 영향을 주면 계획부터 재확인한다. 영향 없는 승인과 구현을 불필요하게 폐기하지 않는다.
- 설계·작업 분해·일반 조회에서는 스펙만 읽는다. 소스, 설정, 의존성 파일을 탐색해 빈 정보를 자동 보충하지 않는다. 스펙에서 확인되지 않는 것은 미구현으로 단정하지 않는다.
- 정보가 부족하면 부족한 점을 설명하고 질문한다. 코드 확인은 사용자가 해당 확인을 요청·허용했을 때 수행한다. 개발 단계에는 현재 작업에 필요한 코드 확인이 포함된다.
- `features/` 및 조회용 색인에는 최종 확인된 내용만 반영한다. 진행 중 내용은 `drafts/`와 `progress.yaml`로 관리한다.
- 조회와 아이디어 제안은 독립 기능이다. 이를 실행했다고 파이프라인을 시작하거나 파일을 수정하지 않는다.
- 중단·재개와 단계 이동에는 [진행 상태](references/progress.md)를 사용한다. 상태 기록을 사용자 승인으로 취급하지 않는다.
