# Project Pilot

프로젝트의 `doc/spec/`를 지속적인 맥락으로 사용한다. 경로는 파일시스템 루트가 아닌 대상 프로젝트 루트 기준이다. 사용자에게는 한국어로 설명하되 기존 프로젝트의 명명 관례를 따른다.

## 스킬 원본 수정 범위

- 이 스킬의 원본 저장소는 `https://github.com/Kchangwook/AI-Native`이며 원본 경로는 `skills/project-pilot/`이다. 다른 프로젝트에 설치된 스킬은 읽기 전용 지침으로 사용한다.
- 스킬 내용을 편집하기 전, 현재 작업 대상이 원본 저장소이고 편집 대상이 그 저장소의 `skills/project-pilot/`인지 확인한다. Git 원격 URL의 HTTPS/SSH 표기 차이와 `.git` 접미사는 같은 저장소로 판단한다. 폴더 이름만 같거나 원본 저장소가 로컬에 존재한다는 이유만으로 수정하지 않는다. 원본임을 확인할 수 없으면 수정하지 않는다.
- 다른 저장소에서 작업할 때는 `SKILL.md`와 참조 문서를 포함한 이 스킬의 파일을 수정하지 않는다. 설치된 복사본뿐 아니라 전역 설치본과 심볼릭 링크의 원본도 수정하지 않는다. 원본 저장소로 이동해 우회 수정하지 않는다.
- 사용 중 지침의 문제나 개선점을 발견하면 제안으로 설명한다. 스킬 변경 작업은 원본 저장소를 작업 대상으로 삼은 대화에서 수행하도록 안내한다.
- 이 범위는 스킬 내용의 편집에 적용된다. 대상 프로젝트의 코드와 `doc/spec/` 수정은 아래 절차에 따라 수행한다. 사용자가 요청한 설치·제거·배포된 버전으로의 업데이트는 별도의 스킬 관리 작업으로 취급한다.

## 요청에 따른 진입

| 요청 | 읽을 지침 | 실행 범위 |
|---|---|---|
| 만들어줘, 기능 추가·변경해줘 | [설계](references/design.md) | 설계부터 시작하여 각 확인 지점에서 대기 |
| 설계해줘 | [설계](references/design.md) | 설계까지만 수행 |
| 승인된 설계를 작업으로 나눠줘 | [작업 분해](references/planning.md) | 작업 계획까지만 수행 |
| 이 설계대로 구현해줘 | [진행 상태](references/progress.md) | 설계·작업 계획의 확인 상태를 점검하고 빠진 단계부터 진행 |
| 계속해줘, 잠시 멈춰 | [진행 상태](references/progress.md) | 저장된 현재 지점에서 재개 또는 중단 기록 |
| 스펙 알려줘, 추가할 기능은? | [스펙 조회](references/query.md) | 조회·설명·제안만 수행 |

진입할 때 필요한 문서만 읽는다. 각 task 시작 전 [task별 새 채팅](references/task-chat.md), 해당 채팅에서 [작업 상세 설계](references/task-design.md), 상세 설계 승인 후 [개발](references/development.md), 리뷰 시 [리뷰](references/review.md)를 읽는다. 문서를 쓰거나 재구성할 때 [스펙 저장 구조](references/spec-storage.md)를 읽는다. 여러 요청이 섞이면 사용자가 요청한 범위를 함께 고려한다.

## 공통 실행 규칙

- 실행 대상 저장소 또는 폴더가 비어 있다면 [프로젝트 기본 설정](references/project-setup.md)에서 기술 스택과 기본 구조부터 정하고, 사용자 확인 후 기능 설계로 진행한다.
- 기본 파이프라인: 기능 설계 → 사용자 확인 → 작업 분해 → 사용자 확인 → task별 상세 설계 → 사용자 확인 → 해당 task 개발·검증·리뷰 → 사용자 확인 → 다음 task에서 상세 설계부터 반복 → 전체 검증 → 최종 확인.
- task 하나당 새 채팅 하나를 사용한다. 계획 승인과 각 task 결과 승인 후 다음 task를 새 채팅으로 인계한다. 상세 설계와 개발·결과 확인은 해당 task 채팅 안에서 수행한다. 자동 생성이 지원되지 않으면 인계 프롬프트를 제공하고 대기한다.
- 각 확인 지점에서 결과를 제시하고 명시적인 진행 응답을 기다린다. 앞 단계 승인이나 최초의 “만들어줘”는 이후 단계의 승인을 대체하지 않는다. 다음 단계의 구현을 미리 시작하지 않는다.
- 수정 요청은 현재 단계에서 반영하고 다시 확인받는다. 확정된 설계에 영향을 주면 설계부터, 작업 계획에만 영향을 주면 계획부터 재확인한다. 영향 없는 승인과 구현을 불필요하게 폐기하지 않는다.
- 기능 설계·작업 분해·일반 조회에서는 스펙만 읽는다. 소스, 설정, 의존성 파일을 탐색해 빈 정보를 자동 보충하지 않는다. 스펙에서 확인되지 않는 것은 미구현으로 단정하지 않는다.
- 정보가 부족하면 부족한 점을 설명하고 질문한다. 코드 확인은 사용자가 해당 확인을 요청·허용했을 때 수행한다. task 상세 설계는 개발 준비 단계로, 이후 개발과 함께 현재 작업에 필요한 코드만 확인할 수 있다.
- `features/` 및 조회용 색인에는 최종 확인된 내용만 반영한다. 진행 중 내용은 `drafts/`와 `progress.yaml`로 관리한다.
- 조회와 아이디어 제안은 독립 기능이다. 이를 실행했다고 파이프라인을 시작하거나 파일을 수정하지 않는다.
- 중단·재개와 단계 이동에는 [진행 상태](references/progress.md)를 사용한다. 상태 기록을 사용자 승인으로 취급하지 않는다.
