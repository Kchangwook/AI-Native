# 빈 프로젝트의 기본 설정

## 적용 조건

기능 설계·개발 요청의 대상 저장소 또는 폴더가 비어 있으면 기능 설계에 앞서 수행한다. Git 저장소가 아닌 일반 폴더에도 동일하게 적용한다. 스펙 조회만 요청한 경우에는 이 단계를 시작하지 않는다.

사용자가 빈 프로젝트라고 명시했거나, 대상 루트의 항목 이름만 확인해 비어 있음을 알 수 있으면 시작한다. `.git`, IDE 메타데이터, 설치된 스킬만 있는 상태는 애플리케이션 기반이 없는 상태로 취급할 수 있다. 빈 상태 확인을 위해 소스·설정·의존성 파일의 내용을 읽거나 재귀 탐색하지 않는다. 파일이 존재하지만 스펙이 없다는 이유만으로 빈 프로젝트로 판단하지 말고 사용자에게 확인한다.

이 확인은 신규 프로젝트 여부를 판단하기 위한 최소한의 항목 조회다. 기존 프로젝트를 스펙 중심으로 파악하는 원칙은 유지한다.

## 기술 스택과 구조 결정

기능 설계에 앞서 프로젝트의 기술 스택과 기본 구조를 정해야 한다고 안내한다. 사용자가 이미 지정한 사항은 유지하고 부족한 결정만 질문한다. 요청한 제품 형태와 규모에 맞는 간결한 안을 제안하며 모든 선택을 사용자에게 새로 떠넘기지 않는다.

다음 중 필요한 항목을 정리한다.

- 실행 형태: 웹·모바일·CLI 등 대상과 FE/BE 필요 여부.
- 기술 스택: 언어, 프레임워크, 패키지·빌드 도구, 저장 방식.
- 기본 구조: 단일 앱 또는 FE/BE 분리, 주요 디렉토리의 책임, 진입점과 실행·검증 방식.

기능의 세부 동작이나 API 설계는 이후 기능 설계에서 다룬다. 현재 요청에 필요하지 않은 서버·DB·인프라를 필수로 추가하지 않는다. 제안한 구성을 설명하고 명시적인 사용자 확인을 기다린다.

## 기록과 다음 단계

`doc/spec/drafts/<change-id>/project.yaml`에 구성안·선택 이유·미정 사항·버전·확인 상태를 기록한다. `progress.yaml`의 `phase`는 `project_setup`, `awaiting`은 기본 설정의 확인 대상과 버전을 가리키게 한다. 기본 설정에 대한 승인도 `approvals.project_setup`에 기록한다. 새 폴더에는 필요한 기록 디렉토리를 생성하되 확정 색인을 만들지 않는다.

승인받은 뒤 [설계](design.md)에서 이 구성안을 맥락으로 사용한다. 기본 설정 승인은 기능 설계나 구현 승인이 아니다. 이 단계에서는 프레임워크 초기화·패키지 설치·앱 파일 생성을 수행하지 않는다. 필요한 초기화는 작업 분해에 선행 작업으로 포함하고 해당 개발 단계에서 수행한다.

수정 요청은 구성안을 보완한 뒤 다시 확인받는다. 구성 변경으로 이미 승인된 설계나 계획에 영향이 있으면 해당 부분도 재확인한다. 확정 스펙과 조회 색인에는 전체 개발·검증의 최종 확인이 끝난 후 실제 구현된 구성을 반영한다.
