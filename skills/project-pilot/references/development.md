# 개발

## 작업 진입

[진행 상태](progress.md)에서 설계와 작업 계획의 승인 버전을 확인한다. 선행 작업의 사용자 확인까지 완료된 작업 하나를 선택해 `in_progress`로 기록한다. 승인되지 않은 계획을 구현하지 않는다.

관련 초안, 확정 스펙, 작업의 완료 조건과 검증 방법을 읽는다. 이 단계에서 현재 작업에 필요한 코드·설정과 직접 연결된 부분을 확인한다. 저장소 전체를 매번 다시 탐색하지 않는다. 스펙의 관련 코드 위치를 우선 활용한다.

코드가 스펙과 다르면 실제 확인한 차이를 기록한다. 승인된 동작이나 작업 범위를 바꿔야 하는 차이는 사용자에게 제시하고 해당 설계 또는 계획부터 재확인한다. 코드에 맞춰 설계를 임의로 변경하거나 확인하지 않은 불일치를 확정 스펙에 반영하지 않는다.

## 구현·검증·리뷰

1. 현재 작업 범위만 구현한다.
2. 완료 조건에 맞는 검증을 수행한다. 영향에 비례한 검증을 선택하고 실행하지 못한 검증은 이유와 함께 기록한다.
3. [리뷰 기준](review.md)을 적용하고 발견한 문제를 보완한다. 변경에 필요한 검증을 다시 수행한다.
4. 구현된 동작·FE/BE 계약·관련 코드 위치를 요청별 초안에 갱신하고, 수행 내용·검증 결과·남은 일을 진행 상태에 저장한다.
5. 작업을 `awaiting_confirmation`으로 바꾸고 결과를 사용자에게 제시한다.

확인 요청에는 구현 내용, 실제 검증 결과, 남은 문제, 직접 확인할 방법, 다음 작업을 포함한다. 확인할 수 있는 증거를 제공한 뒤 기다리며 다음 작업 구현을 시작하지 않는다. 미완료나 검증 실패가 있으면 그 상태를 명확히 밝힌다.

사용자가 승인하면 작업을 `completed`로 기록하고 다음 작업으로 진행한다. 실패한 필수 완료 조건은 단순 승인으로 충족된 것으로 기록하지 않는다. 범위를 변경해 제외하기로 합의했다면 설계·계획을 먼저 갱신하고 재확인한다. 수정 요청은 보완 후 다시 확인받는다.

## 전체 검증과 확정

모든 하위 작업이 확인됐으면 기능 간 사용자 흐름과 연동을 전체 검증한다. 이번 변경에 해당하는 초안과 검증 증거를 정리해 최종 확인을 요청한다. 마지막 작업 승인을 전체 최종 승인으로 간주하지 않는다.

최종 확인 전까지 `features/` 및 프로젝트·도메인 조회 색인을 변경하지 않는다. 최종 확인 후 [스펙 저장 구조](spec-storage.md)의 확정 절차로 스펙과 색인을 함께 반영하고, 진행 상태를 완료 처리한다. 승인 없이 배포·게시 등의 후속 작업을 추가하지 않는다.
