# 스펙 조회와 아이디어 제안

설계·개발과 독립적으로 실행하며 파일을 생성·수정하지 않는다. 조회만 요청받았다면 없는 `doc/spec/`도 만들지 않는다.

## 확정 스펙 조회

1. 대상 프로젝트의 `doc/spec/index.yaml`을 읽는다.
2. 질문에 해당하는 도메인 색인이 있다면 읽고, 필요한 기능 스펙만 읽는다. 전체 스펙과 코드를 매번 읽지 않는다.
3. 질문에 직접 답하고 관련 스펙 파일을 근거로 연결한다. 현재 구현 상태는 마지막으로 확정된 스펙 기준임을 필요한 경우 명시한다.

일반 질문은 최종 확인된 스펙과 색인만 조회한다. 진행 중 변경을 현재 확정 동작으로 섞지 않는다. 사용자가 작업 상태·초안·변경 예정 내용을 물었을 때만 `progress.yaml`과 연결된 초안을 추가로 읽고 확정 내용과 구분한다. 이 질문 자체는 대기 중인 단계에 대한 승인이 아니다.

스펙이나 색인이 없거나 답이 부족하면 확인할 수 없는 범위를 설명하고 질문한다. 미기록을 미구현으로 단정하지 않는다. 조회만으로 색인 복구·디렉토리 재구성·코드 탐색을 시작하지 않는다. 사용자가 코드 확인을 요청·허용한 경우 필요한 부분만 읽고, 스펙에서 확인한 사실과 코드에서 확인한 사실을 구분한다.

## 확장 아이디어

“추가할 만한 기능은?”에는 관련 확정 스펙을 읽은 뒤 목적·기존 기능·제약에 근거해 제안한다. 기존 스펙의 사실과 새로운 제안을 구분하고, 각 제안의 사용자 가치와 주요 의존 관계를 간단히 설명한다.

제안 자체를 설계나 구현으로 취급하지 않는다. 사용자가 특정 제안의 설계·구현을 요청할 때 [설계](design.md)로 진입한다. 별도 아이디어 스킬은 필요하지 않다.
