# 작업 상세 설계

작업 분해가 승인된 뒤 각 task를 실제 수행할 차례에 실행한다. 기능 설계는 무엇을 만들지, 작업 분해는 어떤 단위와 순서로 만들지를 정한다. 이 단계에서는 현재 task를 어떻게 구현할지 구체화한다. FE/BE 하위 작업 각각에 적용하며, 계획 승인을 상세 설계 승인으로 대체하지 않는다.

## 작업 선택과 맥락

이 단계는 [새 채팅 인계](task-chat.md)로 배정받은 task 채팅에서 수행한다. 계획 채팅 또는 다른 task 채팅이라면 먼저 인계하고 여기서 상세 설계를 시작하지 않는다. 현재 task 재개는 기존 채팅을 사용한다.

[진행 상태](progress.md)에서 기능 설계·작업 계획의 승인 버전을 확인하고, 선행 작업의 결과 확인까지 완료된 task 하나를 선택한다. `phase: task_design`, 해당 task의 `status: designing`으로 기록한다.

관련 확정 스펙, 기능 설계 초안, 승인된 계획, 선행 작업 결과를 읽는다. 이 단계는 개발 준비이므로 현재 task에 필요한 코드·설정과 직접 연결된 부분만 확인할 수 있다. 아직 없는 파일은 생성 예정으로 표시하고, 이 단계에서 코드 수정·프로젝트 초기화·패키지 설치를 실행하지 않는다. 전체 코드를 탐색하거나 기능 설계 단계로 코드 탐색 범위를 확대하지 않는다.

## 상세 설계 내용

현재 작업에 해당하는 항목만 구체화한다.

- 구현 범위와 변경·생성할 파일 또는 모듈, 각각의 책임.
- 구체적인 처리 순서, 데이터 흐름, 상태 변화와 예외 처리.
- FE라면 화면·컴포넌트 구성, 상태 관리, 사용자 입력과 API 연동 방식.
- BE라면 API 처리 흐름, 검증, 저장 모델과 관련 로직.
- 기존 코드와 연결할 지점, 선행 작업·계약에 대한 의존 관계.
- 완료 조건별 검증 방법과 주요 실패·회귀 사례.

불필요한 코드 전체를 미리 작성하지 않는다. 기존 설계 내용을 반복하는 대신 구현 선택과 그 이유를 설명한다. 승인된 동작·API 계약·작업 범위를 바꿔야 하면 상위 기능 설계 또는 작업 계획부터 재확인한다.

## 기록과 확인

`doc/spec/drafts/<change-id>/tasks/<task-id>.yaml`에 `task_id`, 기능 설계·계획 기준 버전, 상세 설계 `revision`, 위 구현 내용과 `approval: pending`을 저장한다. `progress.yaml`의 해당 task에 문서 경로·버전과 `design_confirmation`을 연결한다.

상태를 `awaiting_design_confirmation`으로 바꾸고 사용자에게 구현 방식·변경 범위·검증 방법·미정 사항을 설명한다. `awaiting`은 task ID, 상세 설계 확인 종류, 버전을 식별해야 한다. 명시적인 응답을 받을 때까지 구현하지 않는다.

수정 요청은 상세 설계에 반영하고 버전을 올린 뒤 다시 확인받는다. 승인받으면 해당 버전과 승인 근거를 기록하고 [개발](development.md)로 진행한다. 상세 설계 승인과 개발 결과 승인은 별도다.

다음 task는 이전 task의 구현 결과 확인 후, 그 결과를 반영해 상세 설계한다. 모든 task를 한꺼번에 상세 설계하고 일괄 승인받은 것으로 처리하지 않는다.
