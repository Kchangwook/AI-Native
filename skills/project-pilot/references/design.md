# 설계

## 입력과 맥락

1. [진행 상태](progress.md)를 확인해 새 요청인지 기존 작업의 후속인지 판단한다. 승인 대기 중 단순 질문을 받은 경우 기존 대기 상태를 유지한다.
   새 작업의 대상이 빈 저장소·폴더라면 [프로젝트 기본 설정](project-setup.md)을 먼저 수행한다. 기본 설정 확인 전에는 기능 설계안을 작성하지 않는다.
2. [스펙 조회](query.md) 방식으로 프로젝트 색인에서 관련 확정 스펙을 찾는다. 기존 초안에 관한 요청이면 해당 초안도 읽되 확정 스펙과 구분한다.
3. 현재 스펙으로 파악되는 기존 기능, FE/BE 구성, 필요한 기반 요소를 정리한다. 기본 화면·라우팅·서버·저장 환경이 존재한다고 가정하지 않는다. 스펙에 기록되지 않은 요소는 질문으로 확인한다.
4. 결정에 필요한 정보가 부족하면 질문한다. 제안을 곁들일 수 있지만 답을 받은 것으로 처리하거나 코드를 탐색하지 않는다. 사용자에게 맡겨진 작은 선택은 제안 또는 가정으로 설계안에 명시한다.

## 설계 산출물

요청 규모에 맞게 다음 다섯 항목을 작성한다.

- 목적: 대상 사용자와 해결하려는 문제.
- 기능 범위: 이번 요청에 포함할 것과 제외할 것.
- 사용자 흐름: 진입부터 결과 확인까지의 흐름.
- 동작 규칙: 입력·출력, 상태 전이, 예외와 실패 처리. 필요한 화면·API 계약·데이터 구조 및 기존 기능과의 관계를 포함한다.
- 완료 기준: 구현 결과로 확인할 수 있는 조건.

FE 또는 BE만 필요한 기능에는 불필요한 다른 계층을 만들지 않는다. 향후 확장 아이디어를 필수 설계 단계로 추가하지 않는다. 아이디어 요청은 조회 후 추론으로 처리하고 사용자가 채택할 때 설계에 포함한다.

## 저장과 확인

[스펙 저장 구조](spec-storage.md)에 따라 요청별 초안을 `doc/spec/drafts/<change-id>/design.yaml`에 저장한다. 이 단계에서는 세부 작업을 분해하지 않는다. 초안에는 변경하려는 기존 기능 ID와 현재 확정 스펙 경로를 연결한다.

`progress.yaml`에 설계 확인 대기를 기록하고, 다섯 항목과 미정 사항을 사용자에게 읽기 쉽게 설명한다. 사용자 확인 전에는 작업 분해로 넘어가지 않는다.

승인받으면 승인 기록과 설계 버전을 갱신한다. 설계만 요청했다면 종료한다. 전체 구현 요청이거나 작업 분해를 추가로 요청받았다면 [작업 분해](planning.md)로 진행한다. 설계 승인은 최종 스펙 게시 승인이 아니므로 확정 스펙과 색인은 갱신하지 않는다.
